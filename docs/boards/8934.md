# Board 8934: HP Victus 16-e0xxx (AMD)

| Field | Value |
|---|---|
| Product | Victus by HP Laptop 16-e0xxx |
| Board | 8934 |
| CPU / GPU | Ryzen 5 5600H, Radeon RX 5500M |
| BIOS | AMI F.19 (2023-10-17) |
| EC firmware | 80.73 |
| Keyboard | single-colour backlight (driver reports "Normal keyboard") |

## Summary

The BIOS reports **no** software fan support (`GET_SYSTEM_DESIGN_DATA` byte 4 is 0),
but its ACPI tables implement the same GM (`0x20008`) fan commands as Victus S boards.
Manual control works once GM `0x10` has put the EC into user-defined mode.

The difference from Victus S: a GM `0x2E` target of 0 is not "automatic" here. With the
EC in user-defined mode it stops the fan. The driver handles this with the
`zero_rpm_stops_fans` fan-profile flag.

## ACPI (DSDT, `\_SB.WMID`)

| GM cmd | Method | Effect |
|---|---|---|
| `0x10` | `GM10` | `EC0.OMCC = 1` (user-defined fan mode); returns fan count 2 |
| `0x11` | `GM11` | Fan speed read (`FMR1`, `FSUS`, `FS1H`) |
| `0x26` / `0x27` | `GM26` / `GM27` | Read / write `EC0.FFFS` (max fan) |
| `0x2D` | `GM2D` | Fan speeds from `RPM1..RPM4`, in hundreds of RPM |
| `0x2E` | `GM2E` | `EC0.SRP1 = buf[0]`, `EC0.SRP2 = buf[1]` (targets, hundreds of RPM) |
| `0x2F` | `GM2F` | Fan table (only the `GPUT == 2` branch has data) |

Nothing in ACPI ever clears `OMCC`. The EC firmware does that on its own, about 120 s
after the last GM `0x10`.

## EC map (`ERAM`, EmbeddedControl region)

| Name | Offset | Meaning |
|---|---|---|
| `SRP1` | `0x34` | Fan 1 (CPU) target, ×100 RPM |
| `SRP2` | `0x35` | Fan 2 (GPU) target, ×100 RPM |
| `OMCC` | `0x62` bit 0 | User-defined fan mode armed |
| `GPUT` | `0xAF` | GPU type; selects the fan-table branch |
| `RPM1..RPM4` | `0xB0`–`0xB3` | Fan speed, low/high byte per fan |
| `FFFS` | `0xEC` bit 2 | Max fan mode |

## Hardware test log (2026-11-17, kernel 7.3.4)

Run with `tools/fanlab` at about 31 °C idle. The fans sit at about 2000 / 2200 RPM in EC auto.

| Step | Result |
|---|---|
| GM `0x2E` alone (stock driver, forced) | Accepted, fans ignore it |
| GM `0x10` then `0x2E` fan 1 = 3500 | Fan 1 held 3489–3517 RPM for 160 s, with keep-alive at 90 s |
| Back to auto via `0x10` + `0x2E {0,0}` | **Both fans 0 RPM for about 140 s**, then the EC curve resumed |
| Back to auto by clearing max only and letting `OMCC` lapse | Fans held their target for about 90 s, then the EC curve took over; lowest reading 1980 RPM |
| Max then auto (no `OMCC` arm in max) | 4587 / 4697 RPM peak, then back to about 2000 / 2200; lowest reading 1980 RPM |

### With this driver (`pwm1_enable` and `pwm1`/`pwm2`)

| Step | Result |
|---|---|
| `pwm1` write while in auto | Refused (`EINVAL`) |
| Manual, then `pwm1 = 162` | Fan 1 held about 3300 RPM for 150 s through the keep-alive |
| Manual to auto | Target held for about 80 s, then the EC curve took over; lowest reading 1989 RPM |
| Max to auto | 4510 / 4697 RPM peak, then about 2000 / 2200; lowest reading 1983 RPM |
| Max to manual (`pwm2 = 140`) to auto | Manual 3599 / 2894 RPM, then back to EC auto; lowest reading 1967 RPM |

The pwm-to-RPM round trip truncates twice, so `pwm1 = 162` (about 3500 RPM) lands at
3300, and `pwm2 = 140` reads back as 129. This affects all boards.
